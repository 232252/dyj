# ADR-0001：仓库与版本控制基线

- **状态**：已接受
- **日期**：2026-02（会话日期）
- **决策者**：项目发起人

## 背景

项目目录此前为空。在写下任何代码之前，需要先有一份可长期演进、适合多人协作的仓库基线。
项目价值观（体积小、好维护、长眼光、无巨石）要求仓库结构从第一天起就反映模块边界，
而不是先堆代码、以后再拆分。

## 决策

1. **使用 Git，主分支名为 `main`**（`git init -b main`）。
2. **提交换行符统一**：通过 `.gitattributes` 将仓库内文本规范化为 `LF`；
   `*.ps1`/`*.bat`/`*.cmd` 强制 `CRLF`，`*.sh` 强制 `LF`。理由：项目要同时支持
   Linux 与 Windows，换行符不一致会造成 `bash: $'\r': command not found` 这类难查故障。
3. **`.gitignore` 覆盖多语言构建产物**（Rust `target/`、Go `bin/`、Node `node_modules/`、
   Python `__pycache__/`、CMake 产物），因为在技术选型确定前需要保持选择自由。
4. **文档先行**：调研结论进 `docs/research/`，非平凡决策进 `docs/adr/`。
   `docs/research/*.local.md` 被忽略，用于个人草稿。
5. **不提交二进制打印测试样本**（`*.pwg`、`*.urf` 等）到主仓库；测试样本应由脚本生成或
   放在外部资源，避免仓库膨胀 —— 与"体积小"价值观一致。
6. **不提交任何真实凭据**；`.env` 系列默认忽略，仅放行 `.env.example`。

## 备选方案与拒绝理由

| 方案 | 拒绝理由 |
| --- | --- |
| 直接用 GitHub 模板 + 预选语言脚手架 | 技术选型尚未调研，过早绑定会污染仓库结构 |
| 单一巨型 `.gitignore`（只针对某一语言） | 选型未定，需保持多语言中立 |
| `CRLF` 全仓库 | Linux 为主的服务端目标平台上会出问题 |
| 提交 PDF/PWG 测试样本以简化 CI | 二进制样本会持续膨胀仓库；应改为脚本生成 |

## 后果

- **正面**：任何语言的实现都能直接落地；跨平台换行符问题被前置消除；决策可追溯。
- **负面**：`.gitignore` 较长，需要维护；若最终单语言实现，可裁剪无关小节。
- **风险**：`* text=auto eol=lf` 在含既有 `CRLF` 文件时可能产生一次性的巨大 diff ——
  目前仓库为空，无此风险。
