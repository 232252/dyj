# ADR-0017 · 恢复 631 IPP 别名监听（仅数据面）

日期：2026-11-14
状态：已实施（0.7.0）
取代：ADR-0014 中对 631 别名的回退决定（其余回退维持不变）

## 背景

ADR-0014 把 631 别名、配对即信任 IP、鸿蒙接收端 App 一并回退，理由是
"开放打印模式对任何平台系统打印栈适用"。2026-11-14 现场证伪了这一点：

- 鸿蒙平板「IP添加」只有名称 + IP 字段，**没有端口输入，隐含 631**
  （research/17 §4 真机实证，华为官方指南同口径）；
- 服务只监听 6631，631 无人监听 → 平板按 IP 添加必然建连失败；
- 开放打印模式已确认生效（`open_print_always=true`），但**免认证解决的是
  401，解决不了端口不匹配**——"无密码还是不行"的根因即此。

自动搜索（mDNS）路径的 SRV 记录带真实端口，理论上可用，但依赖组播穿透
（AP 隔离/防火墙/平板 mdnsmanager 缓存都可能挡），不能作为唯一通道。

## 决策

恢复 `startIPPAlias`（commit 6660e7c 的实现，按当前代码结构重装配）：

1. 共享角色节点在主端口绑定后，best-effort 监听 `:631`；被占用或无权限
   （真实 CUPS、Linux <1024 非 root）**跳过而非报错**，主端口契约不变，
   mDNS SRV 仍指向主端口。
2. 别名**仅数据面**：`aliasGuard` 只放行 `/ipp/…` 与 `/p/<token>/…`，
   其余路径 404。IPP 路由器本身对未知路径宽容（回落默认打印机），
   没有这层防护 /admin 会在 631 上可达——测试钉死。
3. 别名走独立的 `ippOnly` swapHandler，与主路由同步热更新；停机一并
   Shutdown。
4. 门禁不变：别名上的请求同样过 loopback/开放窗口/配对令牌检查。
   平板免配对直连依赖开放打印模式（用户显式开启），不引入 IP 信任。
5. 防火墙三处同步：doctor 检查（`IPPAlias` 参数）、一键修复
   （`dyj IPP Alias` 规则，按程序路径清理）、安装器预置规则。

## 后果

- 平板/手机系统打印「按 IP 添加」零配置可用（配合开放打印模式）。
- 631 被真实 CUPS 占用时行为与 0.6.0 完全一致（跳过）。
- 攻击面不扩大：别名与主端口同一门禁；管理面仍只在主端口。
- ADR-0014 的其余决定（裁撤鸿蒙 App、不做配对即信任 IP）维持不变。
