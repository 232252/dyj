# ADR-0013 · HarmonyOS 端改为"系统打印接管"

日期：2026-11-09
状态：已接受（真机实验结果见调研 17 §4，回填后定稿）
取代：ADR-0012 的"App 内四步闭环"方向（部分取代——配对/发现 UI 保留，打印动作移交系统）

## 背景

ADR-0012 选择"App 内打印"（发现 → 配对 → 选内容 → App 内发 IPP），当时否决"交给系统打印"的理由是一句未取证的判断："鸿蒙没有 AirPrint 那样的系统级 IPP 客户端可用"。用户实际使用后提出：**配对连接一次之后应由系统打印接管**——系统打印面板里出现这台打印机，任意应用都能打印，而不是在 dyj App 里选文件。

## 取证结论（调研 17）

1. 三方 App 注册打印服务扩展的路被系统接口关死（`PrintExtensionAbility` 仅系统应用；`PRINTER_DRIVER` 受限审批且仅 PC）。
2. 但系统自带打印栈是 CUPS 血统且入口存在：设置 → 打印机和扫描仪 → 添加（自动搜索 mDNS + IP添加）；平板上实测 `print_service` + `cupsd` 在跑。
3. dyj 服务端 IPP Everywhere 全套操作早已齐备，CUPS 客户端（`-m everywhere`）已实证可直连打印（调研 12）。
4. 唯一冲突是 401 配对门禁：系统打印客户端带不了 URI 路径令牌。

## 决策

1. **数据面**：新增"配对即信任设备"——App 配对一次后，服务端按设备源 IP 放行免令牌 IPP（commit 196f55f）。撤销设备同时断令牌与 IP 信任。威胁模型维持"阻断随意蹭打"级别（与 4 位 PIN 一致）。
2. **HarmonyOS 端形态**：dyj App 从"打印工具"收缩为"配对/管理助手"——扫描、配对、状态展示保留；内容选择与打印动作交给系统打印面板。App 内打印 UI 在系统接管验证通过后裁撤。
3. **服务端为第一公民**：任何能让系统打印客户端"发现/添加"dyj 广播的改进（mDNS TXT、端口约定、TLS）优先在服务端做，端侧零维护。

## 后果

- 正面：打印体验与平台惯例一致（图库/WPS/浏览器直接打印）；App 大幅瘦身；与 Windows/CUPS 侧"添加系统队列"的既有路线对齐成同一个模型（服务器伪装成普通 IPP 网络打印机）。
- 代价/风险：受信按 IP 记录，DHCP 换址需重新配对（管理页可查受信设备）；系统客户端行为（端口假设、文档格式偏好、TLS 要求）以真机实验为准（调研 17 §4 关注点）。
- 回滚：服务端信任分支独立于令牌路径；出问题撤销设备或回退二进制即可。

## 验证

调研 17 §4 真机实验（平板系统面板添加 dyj 打印机 → 系统打印 → dyj 队列出现任务）。
