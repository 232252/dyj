# ADR-0012：鸿蒙接收端走 React Native 鸿蒙化（RNOH），协议在 TS、平台在 ArkTS

- **状态**：已接受
- **日期**：2026-11-08
- **依据**：[调研 16](../research/16-harmony-receiver-design.md)（版本矩阵、SDK 取证、
  服务端协议事实、踩坑记录）
- **前置**：[ADR-0005](0005-single-wire-encoder.md)（单一 wire 编码器）、
  [ADR-0010](0010-role-wizard-pairing.md)（4 位码配对与 URI 路径令牌）、
  [ADR-0011](0011-minimal-two-mode-ui.md)（文案禁用词是硬约束）

## 背景

dyj 目前的接收端形态是「在 Windows/macOS/Linux 上装本机程序，把共享端的队列装进
系统打印队列」。这条路在手机上走不通：手机没有「装系统队列」这回事，用户要的也
不是「把打印机装进手机」，而是**「从手机把东西打出去」**。

于是要有一个手机端程序，闭环是：**发现共享端 → 输入 4 位配对码 → 选内容 →
打印**。首版支持图片 + 文本 + PDF。

约束很硬：

1. **服务端零改动**。配对走 `POST /pair`，打印走 `POST /p/<令牌>/ipp/print/<打印机>`，
   都是现成接口；不动 wire 格式、不动令牌语义、不碰 `/admin/api/*`。
2. **wire 格式不能漂移**。仓库既有规矩：IPP 字节布局由 `pkg/attributes` 单一编码器
   负责，且有黄金字节锁定。手机端是第二套实现，必须与 Go 侧逐字节一致。
3. **界面文案禁用工程术语**（ADR-0011 D4）。

## 决策

### D1. 技术路线用 RNOH（React Native 鸿蒙化，New Architecture）

版本线：**RN 0.84.1 + RNOH 0.84.5 + CLI 20.1.0 + react 19.2.3**。包名
`com.dyj.app`。

选它而不是原生 ArkTS / ArkWeb 薄壳：协议层要能单测、要能与 Go 侧共用黄金字节，
这两件事只有在「协议写 TS」的前提下才成立；ArkWeb 薄壳则拿不到系统文件选择器
与沙箱路径。

### D2. 协议编解码在 TS 侧，平台能力在 ArkTS TurboModule 侧

TS 侧负责：IPP 编解码、mDNS 报文解析、实例去重、格式协商、错误到人话的映射。
ArkTS 侧只提供六类原子能力：`DyjHttp`、`DyjMdns`、`DyjPrefs`、`DyjFiles`、
`DyjImage`、`DyjPdf`。

理由：协议层是**要被测试反复咬住的部分**，放在 TS 里才有单测；平台能力天然属于
系统，放 ArkTS 里才不用自己造轮子。

### D3. TurboModule 跨桥只传字符串

六个模块一律返回字符串（JSON 串或 base64）。大文档用「头 base64 + 文档 base64」
两段过桥，ArkTS 侧解码后拼接再发出。

理由：codegen 对 ArrayBuffer 与复杂对象的支持有限，传字符串是最稳的形态；两段式
保证大文件不必先整份复制进 JS 内存。

### D4. 黄金字节单一事实源仍是 `pkg/client/testdata/print_job.hex`

Go 侧生成它，Go 与 TS 各自读取断言。手机端不另立一份「自己的」期望值。

### D5. PDF 默认在端上渲染成逐页 JPEG 逐页打印

服务端**只有装了 poppler 才声明 `application/pdf`**（`pkg/driver/pdf.go`）。所以默认
路径用手机的 PDF Kit 逐页渲染，逐页一个作业；「保持原样直传」是可选开关、**默认
关闭**，且只在服务端明确声明支持时才出现在界面上。

理由：默认路径必须对「任何服务端」都成立；把能力差异交给用户去判断是不人道的。

### D6. mDNS 扫两轮，去重键是实例全名

服务端对「有哪些打印服务」只回 PTR，对「这个服务在哪」才回 SRV/TXT/A，所以手机端
先扫一轮拿实例名，再带着实例名扫第二轮。去重按**实例全名**（不是主机名），多网卡
的多个端点全部保留——共享端在多网卡机器上会为同一实例发布多条 SRV 与 A 记录。

### D7. 服务端零改动，配对码与令牌不进日志

手机端不新增任何服务端接口、不改任何服务端行为。手机本地保存配对令牌（打印路径
里要用），但**不写进日志**（仓库既有约束：令牌与配对码不落日志）。

### D8. 签名归用户，仓库不留签名材料

仓库 `signingConfigs` 留空，交付**未签名 HAP** + 签名步骤说明。禁止复用本机其它
工程的证书与 profile。

### D9. Windows 上的 MAX_PATH 必须在构建配置里解决

ohpm 生成的导入目标把 `.ohpm` 虚拟 store 的绝对路径写进 include 目录，Windows 上
加头文件名超过 260 字符，ninja 记录依赖会直接失败。解法是把导入目标的 include
目录换回 `oh_modules/@rnoh/...` 的目录联接路径（同一份内容，短 80 字符），改在
`harmony/entry/src/main/cpp/CMakeLists.txt` 里，不靠「清缓存碰运气」。

## 备选方案与拒绝理由

- **原生 ArkTS 全写**：协议层没有单测载体，黄金字节对齐要另写一套工具；工作量
  翻倍且违反仓库「wire 改动必须黄金字节测试」的约束精神。
- **ArkWeb 内嵌管理页**：管理页是给共享端机器看的；手机端需要系统文件选择器、
  相册、沙箱路径，Web 壳做不到。
- **把 IPP 打印交给系统**：鸿蒙没有 AirPrint 那样的系统级 IPP 客户端可用，
  iOS/iPadOS 的系统打印不暴露给第三方 App。
- **在 TS 里跑 zip/gzip 压缩文档**：省不了多少带宽，却把复杂度搬到 JS 侧；服务端
  只在声明 `compression=gzip` 时才解压，不声明就是原样收。
- **手机端直连打印机（IPP Everywhere / AirPrint）**：不解决「共享端在哪、怎么配对」
  这个真问题；共享端是本仓库的服务端，与手机直连打印机是另一条产品线。

## 后果

- 新增 `harmony/dyj-harmony/`（RN 工程 + ArkTS 工程），仓库 Go 侧**零改动**。
- 协议层有两套实现（Go 与 TS），用**同一份黄金字节**把住漂移。
- 首版不支持相机直拍、不支持系统分享、不支持后台常驻发现。
- 跨网段发现仍是服务端议题（调研 15），手机端只有「按地址添加」兜底。
- 签名、装机、真机验收由用户完成（调研 16 §8 的第 5–7 条）。
