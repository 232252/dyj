# ADR-0004：P0 实证计划（从调研转入实现）

- **状态**：已接受（Accepted）
- **日期**：2026-02（会话日期）
- **决策者**：项目发起人
- **依据**：[ADR-0002 技术栈与架构](0002-stack-and-architecture.md)、[ADR-0003 许可证](0003-license.md)、[调研索引的 P0 清单](../research/README.md)

## 背景

仓库已有一份完整的 Phase 0 调研（8 份文档、~180 个来源），结论是：
**IPP + DNS-SD + Go + "转发给已有打印队列"**。

但调研索引明确列出了一份 **P0 待实证清单**，其中第 1 项写着：

> **自研 IPP 服务端能否被 Windows 11 直接添加成功？**
> **本项目核心验收标准**；若不成立则整个方案不成立。

调研阶段**没有回答这个问题**——因为当时没有写任何代码。本 ADR 决定：
**停止增加调研文档，转入实证**。理由：调研文档已达上限，边际收益递减；
而最大的风险（"这条路到底走不走得通"）是**只能靠代码回答**的，不是靠再读几篇 RFC。

## 决策

### D1. 本轮目标是"可运行原型 + 实证结论"，不是"完整产品"

范围严格限定为回答核心验收标准所需的最小闭环：

```
pkg/attributes/   带显式 tag 的 RFC 8010 属性写入器 + IPP Everywhere 属性表   ← 最大空白
pkg/ipp/          HTTP 层 + Get-Printer-Attributes 操作
pkg/discovery/    mDNS/DNS-SD 通告 _ipp._tcp（显式指定接口）
cmd/dyj/          CLI 入口（只做装配）
```

**明确不做**（留给后续版本）：`Print-Job` 实际投递、`driver/winspl` 后端、作业队列持久化、
Windows 服务封装、安装包、Web UI。理由是这些都以"客户端愿意把我们的打印机加进来"为前提——
**前提不成立，做这些全是浪费**。

### D2. 风险最高的一块优先做：`pkg/attributes/`

[附录 E](../research/07-go-ipp-server-capability.md) 已实证：`go-ipp v1.7.0` 的
`AttributeTagMapping` **只认识 70 个属性名**，缺少**几乎所有** IPP Everywhere 必需的
`-supported` / `-default` 属性，且 `Encode` 遇未知属性**直接报错、无绕过参数**。

**这不是可以绕过的细节**：没有能力声明，客户端根本不会发作业。
所以"自研带显式 tag 的属性写入器"是本项目的**第一块必须自己写的代码**，
且它必须用**黄金字节单测**锁定正确性（手写 RFC 8010 是本项目最易错之处）。

### D3. 许可证已定：**Apache-2.0**（关闭 ADR-0003 的待决项）

发起人拍板**保留未来商业化路径** → 必须避开 copyleft 传染 → 选 Apache-2.0。
这与 CUPS、`go-ipp` 一致，且允许自由借鉴 `ipp-usb`（BSD-2-Clause）代码。

### D4. 验收必须"可复现"，且**失败的详细记录优于含糊的成功**

本项目的验收标准是**外部可观察行为**，不是单测绿灯：

| # | 验收项 | 判定方式 |
| --- | --- | --- |
| A1 | 属性字节编码符合 RFC 8010 | 黄金字节断言（手工推导 vs 实现输出逐字节比对） |
| A2 | 服务端能正确响应 `Get-Printer-Attributes` | 真实 IPP 请求 → 响应可被解码且属性齐全 |
| A3 | mDNS 能被发现 | `_ipp._tcp` 服务实际可见 |
| A4 | **Windows 11 能直接添加该打印机** | Win11「添加打印机」实际走到哪一步 |
| A5 | 体积小 | 实测二进制大小 vs "拖 500MB 运行时"反面例子 |

**A4 是唯一真正定义项目成败的一项。** 若 A4 失败，前四项全部作废——但**失败的详细
错误码与卡点本身就是高价值产出**，因为它把"未知风险"变成了"已知的具体问题"。

### D5. 代码产出必须再经一轮对抗性核查

上一轮调研的对抗性核查**推翻过 3 项结论**（见[附录 F](../research/08-independent-review.md)），
证明该流程有效。代码比文档更易藏错（尤其是手写二进制协议），因此：
**新增代码必须由独立一方以"试图推翻"的方式复核**，且核查者的字节向量必须
**独立从 RFC 8010 原文重新推导**，不得读实现后复述。

## 备选方案与拒绝理由

| 方案 | 拒绝理由 |
| --- | --- |
| 继续补调研文档，不写代码 | 核心验收标准**只能靠代码回答**；调研文档已 8 份、~180 来源，边际收益递减 |
| 直接开写完整产品（含 Print-Job、驱动后端） | 前提（A4）未验证；若 A4 失败则大量工作作废 |
| 先用现成 IPP 服务端（CUPS/ippsample）验证再自研 | 可作为对拍基准，但 CUPS 在 Windows 上不存在（见 ADR-0002 D1），且无法回答"**自研**能否被 Win11 接受" |
| 跳过对抗性核查以省时间 | 上轮核查推翻 3 项结论；手写协议字节是本项目最高错的环节 |

## 后果

- **正面**：把项目最大的未知风险（A4）在写任何产品代码前解决；`pkg/attributes/` 一旦用黄金字节锁定，
  就是整个项目最稳的一块地基；许可证问题关闭。
- **负面**：本轮不产出"能用的产品"，只产出原型与结论。若 A4 失败，需要重新评估
  `driver/winspl` 之外是否需要补 `driver/ippusb` 等路径。
- **风险**：
  1. **本机无 `ipptool`**（CUPS 测试套件未安装），P0 #5「通过官方一致性测试套件」**本轮无法完成**，
     只能用自研黄金字节 + 手工核对替代。这是本轮验证的**已知弱点**，必须如实标注。
  2. **目标打印机当前离线**（[附录 C.4](../research/05-environment-probe.md)），
     真机出纸验收可能无法完成；此时 A4 只能验到"添加成功"，验不到"打得出纸"。
  3. 本机 **4+ 网段 + 3 个 APIPA 接口**，mDNS 通告必须显式选接口，否则验证会假阴性。
